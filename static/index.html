Software

Overview

GroundLoop answers a question from its own documents, checks that answer, and tries to repair it when the check fails. Every step is saved, so the result can be inspected rather than trusted on its own.

It is a standalone system. The question came from evaluation work on a campus assistant, and GroundLoop has not been built into that assistant. The Duke Kunshan collection used in the study is a benchmark made from public Duke Kunshan pages, not a deployed chatbot.

1Core library

Python. Retrieves, generates, evaluates, diagnoses, recovers, and verifies. It also runs the benchmark.

2HTTP adapter

Exposes the library. The core never imports the adapter.

3This console

Renders only what the adapter returns. One query writes one trace, and Reliability is computed from those files.

Software

The loop

One question goes through six stages. A retry happens only while the recovery budget remains.

  1. RetrieveThe closest passages.
  2. GenerateAn answer from those passages.
  3. EvaluateA language-model judge, plus checks for spans and sources.
  4. DiagnoseWhy the answer failed, when it did.
  5. RecoverRewrite the question, widen retrieval, regenerate, or abstain.
  6. VerifyAccept, retry, or abstain.

Pauses after the diagnosis and waits for approval.

Auto recovery

The whole loop. Demonstrations use depth 4 and at most two actions.

Reliability lists every run with the first answer, the action, the passages, and the verdict. Filter by verdict, action, policy, or diagnosis. Data shows the documents the system retrieved from.

Software

Verdicts

The judge never sees the answer key. Gold is used only after a run, to score it.

A verdict of improved means the system's own check changed in the direction it treats as better. It is evidence you can open. It is not proof that the answer became correct.

Still failing means the check did not pass after recovery. That covers a correct refusal, when the documents do not contain the fact, and a failed repair, when recovery ran and the answer still did not clear the check.

Study

Design

The same engine as this console, in automatic mode, on three small collections.

88questions, three collections, three repeats
1, 2, 4passages for the loop and a retrieve-once baseline
8passages for a plain baseline, the cheaper comparison

Lower retrieval depth makes the first pass miss more often, so there is something for recovery to fix. The 8-passage baseline tests whether simply fetching more matches the loop at lower cost. The judge, the diagnosis, and the verifier see the question, the passages, and the answer. They do not see gold.

Study

Results

With one passage, the loop raised the rate of correct answers. A wider search matched that quality for less than half the cost.

0.81 → 0.97Duke Kunshan, one passage
1.00Harbor and Kestrel, one passage
1 in 27loop runs was an actual regression
76 / 98diagnoses matched the gold class
59 / 73verdicts matched gold on answerable recoveries
< halfthe cost, for the 8-passage baseline

In one case the loop reported a repair after changing only the source an answer named. What the loop adds, on these collections, is a diagnosis, an action, and a verdict for every answer. The wider baseline is the comparison any claim for the loop has to beat.

Study

Limits

The reading is bounded by the model, the collections, and two open gaps in the software.

  • One model, three repeats, and small single-hop collections.
  • The judge sample is 40 calls and was not an independent blind rating.
  • The Duke Kunshan facts are public, so the model may know some answers without retrieving them.
  • After the recovery budget is used up, an answer can still be recorded as improved when the judge marks it unsupported.
  • The span check ignores one- and two-digit numbers.
